# التقرير النهائي — مكتبة المكونات والاقتراحات (مِرْباح)

> القياسات كلها من قاعدة البيانات بعد التبذير، والاختبارات شُغّلت فعليًا.

## ١) هيكل قاعدة الأنشطة والتصنيفات والمنتجات

```
نوع المنشأة (project) ← النشاط (activity) ← التصنيف (category) ← المنتج (product) ← الاقتراحات (suggestions)
```
- `catalog_activities(key, name, icon, position, visible)`
- `catalog_categories(id = activity:category, activity_key, name, position, visible)`
- `catalog_products(id = activity:category:product, category_id, name, ing_key, position, visible)`
- `catalog_suggestions(ing_key, name, kind, unit, position)` حيث `ing_key` = منتج أو `domain:نشاط`
- `library_items` — مكتبة المكونات العامة (اسم عربي/إنجليزي، تصنيف، وحدة افتراضية، حالة).
- `merchant_items` + `merchant_item_prices` — مكتبة التاجر الشخصية وسجل أسعاره (منفصلة تمامًا).
- `merchant_suggestions` + `suggestion_reports` — اقتراحات التجار والبلاغات للمراجعة الإدارية.

## ٤) كيف يُضاف نشاط أو منتج من لوحة المالك؟

- **نشاط**: `/owner-admin/#/catalog` ← «نشاط جديد» ← المفتاح + الاسم.
- **تصنيف**: النشاط + معرف + اسم.
- **اقتراحات**: `/owner-admin/#/suggestions` ← (منتج أو `domain:نشاط`) ← إضافة + نوع + وحدة.
- **منتج جديد في كتالوج مالك**: يُدار عبر ملف `server/data/catalog-esm.mjs` حاليًا (لا واجهة بعد — مذكور في «تطوير لاحق»).
- **الظهور للتاجر**: فوري عبر `catalog-sync.js` + `/api/public/catalog` — أثبته الاختبار (نشاط «وجبات الحيوانات» ظهر).

## ٥) كيف يُدير التاجر مكتبته الخاصة؟

- «الحاسبة»: يختار من الاقتراحات (تحديد متعدد) ← يملأ حجم العبوة والسعر مرة ← تُضاف كلها للدفتر.
- كل مكوّن يُحفظ في `merchant_items` عند حفظ المنتج: `POST /api/merchant/items` وسعره في `merchant_item_prices`.
- تحديث السعر الجديد بسجل: `PATCH .../items/:id { newPrice }` ← تبقى الأسعار القديمة في السجل (مختبر: سعرين).
- عزل: التاجر الآخر يرى صفر مواد و`404` عند محاولة التعديل (مختبر).

## ٦) مصادر البيانات والتراخيص (تفاصيل: `docs/data-sources.md`)

| المصدر | الترخيص | يستخدم؟ |
|---|---|---|
| USDA FoodData Central | CC0 (عامة) + API بمفتاح (1000 طلب/ساعة) | مؤجل — لا نسخ |
| Open Food Facts | ODbL (مشاركة بالمثل) | غير مستخدم — لا مراجعة قانونية |
| King Arthur Weight Chart | لا ترخيص بيانات | غير مستخدم |
| Craft Yarn Council | معايير + إسناد للرموز | مرجع تسمية فقط |
| GS1 Standards | 403 — لم يُفتح | لا |

**المصدر الحالي للاقتراحات: مسميات من إعداد فريق المنصة** (خبرة المجال)، لا بيانات مسحوبة. لا يوجد ادعاء بأنها بيانات USDA أو غيرها.

## ٧) خدمات API المربوطة فعليًا

- **لا API أسعار فعّال** (Muwazin مفتاح مدفوع، والبواقي بلا API).
- **الذكاء الاصطناعي**: جُهّز `POST /api/merchant/ai-suggest` (المفتاح على الخادم فقط، `server/.env`)، **غير مهيأ** حاليًا (`configured:false`) — يُفحص الشكل والقيم قبل العرض.
- خدماتنا: `/api/public/{catalog,suggestions,library}` · `/api/merchant/{suggestions,report,item(s),usage,ai-suggest}` · `/api/owner/{catalog,library,suggestions-review,reports}`.

## ٩) يحتاج تطويرًا لاحقًا
1. **واجهة مالك لإضافة منتج للكتالوج** (حاليًا عبر ملف ESM).
2. **إعادة ترتيب الاقتراحات بالسحب** + كشف التكرار الآلي بين المكتبة والاقتراحات.
3. **جلب أسعار آلي**: Muwazin مفتاح.
4. **ربط مكتبة التاجر تلقائيًا بالدفتر عند إضافة مكون** (يُسجَّل حاليًا عند حفظ المنتج).
5. **مكتبة وصفات الجاهزة** ومضاعفة الإنتاج وقائمة المشتريات (من المشروع السابق، قابلة للبناء فوق نفس البيانات).
6. **شعار صورة** ورفع ملفات.

## ١٠) النتيجة
التاجر يرى اقتراحات مرتبطة بمنتجه ونشاطه: صاحب العطور لا يرى الكوكيز، والكروشيه لا يرى المخبوزات. كل اقتراح يمر بنفس محرك التكاليف (سعر الشراء × المستخدم ÷ المشترى)، وكل اقتراح تاجر يخضع لمراجعة إدارية قبل أن يصل للجميع.
